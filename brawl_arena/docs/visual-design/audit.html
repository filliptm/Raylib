01 / Verdict

Strong game, fragmented shell

The UI is functional and the code is understandable, but each screen has accumulated its own sizes, colors, interaction details, and layout rules. That makes polish expensive and model-specific problems recurrent.

Keep

What already works

  • Menu cards are connected to real actions.
  • Selected-kit data already drives multiple screens.
  • Objective, ammo, health, ability, and result state are present.
  • Command-center local/project provenance is a strong foundation.
  • Station assets, toon shading, lights, bloom, and ability VFX give the world identity.
Change

What blocks polish

  • No shared font or semantic UI theme service.
  • Hard-coded layouts assume one window shape and one model frame.
  • Mouse interaction exists without a unified focus/navigation model.
  • Rounded cards and frequent pulses flatten screen hierarchy.
  • Player UI and developer tools repeat visual decisions separately.

03 / Highest-value fixes

Start where changes multiply

These investments reduce the cost of every later screen. They also avoid coupling the visual pass to gameplay simulation.

P0 / Foundation

Theme + text

Own font lifetime, semantic colors, type roles, measurement, shadows, and text fitting in one UI layer.

P0 / Composition

Layout + profiles

Add reference-canvas scaling, safe zones, anchors, and per-character preview profiles for home and select.

P0 / Access

Focus + navigation

Unify pointer, keyboard, and controller activation before migrating screens onto new components.

04 / Implementation sequence

Six controlled passes

Each pass should land with a build, architecture check, focused tests, and screenshots at the reference and at least one stress viewport.

  1. Inventory + baselines Capture current home, select, controls, HUD, results, and every command-center tab. Record focus order, click areas, and key UI values before changing presentation.
  2. Presentation foundation Add ui_theme, ui_text, ui_layout, and font assets. Preserve exact existing behavior while routing text and colors through named roles.
  3. Input + components Add focus/navigation state and reusable buttons, panels, keycaps, bars, stat rows, segmented selectors, and text fitting. Include reduced-motion and UI-scale settings.
  4. Menu migration Build the launch deck, roster bay, grouped controls, and result summary. Introduce per-character preview profiles and test every imported/fallback model.
  5. HUD + tool migration Consolidate the objective broadcast, survival and ability docks, action-based tutorials, and match summary. Give command-center controls a wider inspector layout and sticky provenance.
  6. World integration + QA Add a lightweight station/hangar menu context, tune lighting/post effects, verify contrast and color-independent state, exercise controller flow, and compare all baseline screenshots.

05 / Definition of done

Evidence, not vibes

A detail pass is finished when the system survives real content and input, not when one ideal screenshot looks polished.

Visual acceptance
  • All five brawlers and primitive fallbacks fit home/select protected zones.
  • No menu or HUD copy clips at supported UI scales.
  • Primary, secondary, utility, destructive, disabled, focus, and pressed states are distinct.
  • Gameplay remains legible with bloom, outline, and color filters at their supported extremes.
  • Reduced motion removes non-essential orbit, pulse, sweep, and bob effects.
Interaction acceptance
  • Every menu action is reachable by mouse, keyboard, and controller.
  • Focus returns to the invoking control when a modal closes.
  • Mode, selected brawler, config source, dirty state, and save destination are never implicit.
  • Tutorial prompts retire per demonstrated action and can be reset.
  • No attack shakes any user’s camera.
Known platform boundary

Contrast, scaling, reduced motion, focus, and controller navigation are achievable inside raylib. Full operating-system screen-reader semantics would require a deliberate native accessibility bridge and should not be implied by the UI refactor alone.

06 / Files in scope

Likely implementation map

Gameplay mechanics stay outside this pass. The visual system belongs in the player-facing UI layer, with only presentation metadata and asset ownership crossing into presentation/content where appropriate.

Recommendation

Approve the direction, then implement the presentation foundation as a bounded first milestone. Do not begin by restyling all existing DrawText calls in place.
